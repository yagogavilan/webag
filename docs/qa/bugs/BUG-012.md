# BUG-012 | Severidade: Média | Prioridade: P2 | Status: FECHADO em 2026-11-19 (reteste Onda 7)

**Cancelar a corrida pelo admin deixa o pedido em "pronto para coleta", sem corrida e sem estorno (WB-233 C6)**

Ambiente: API commit ae8060f, Postgres e Redis reais. Teste: `qa-onda3-5-lacunas.e2e-spec.ts` (BUG-012, `it.fails`).
Passos: 1. Pedido de entrega pago, aceito, loja marca `ready_for_collection` (corrida nasce). 2. Operação chama `POST /v1/admin/logistics/deliveries/{id}/status` `{action:'cancel', reason}`. 3. Consultar o pedido.
Esperado: WB-233 C6: a corrida vira CANCELADA "e o motivo vai ao pedido" (RN-18: CANCELADA tem "Pedido: conforme o pedido"). O pedido não pode ficar parado.
Obtido: corrida `cancelled` (200), pedido continua `ready_for_collection`, sem corrida ativa e sem estorno. O cliente vê "aguardando o motoboy" para sempre e o cancelamento do cliente é recusado (409 ORDER_NOT_CANCELLABLE nesse estado). Se a loja pode "voltar para separação" nesse estado não foi verificado [HIPÓTESE].
Impacto: pedido pago preso sem desfecho; depende de o operador lembrar de estornar manualmente (e ver BUG-011: o estorno também não encerra o pedido).
Evidência: probe 2026-11-19 e teste `it.fails`. História relacionada: WB-233, WB-234, RN-18.

**Reteste de 2026-11-19 (QA, Onda 7):** Reteste real, seção bug012: 5 de 5. Cancelar a corrida pronta para coleta (`action: cancel`, motivo) encerra o pedido (`cancelled`, ator admin, motivo "Entrega cancelada pela operação: ..."), estorna por inteiro, a loja não consegue "voltar para separação" (409), repetir não estorna de novo (409, estornado = total uma vez) e cancelar uma corrida já atribuída a motoboy também encerra o pedido.
