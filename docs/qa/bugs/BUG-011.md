# BUG-011 | Severidade: Alta | Prioridade: P1 | Status: FECHADO em 2026-11-19 (reteste Onda 7)

**O admin não tem como cancelar um pedido; o estorno total manual deixa o pedido ativo e a loja ainda o aceita (RN-08, WB-109, SEC-151)**

Ambiente: API no commit ae8060f, Node 22, Postgres 16 e Redis reais, provedor `fake`. Teste: `apps/api/test/qa-onda3-5-lacunas.e2e-spec.ts` (BUG-011 e 011b, marcados `it.fails`).
Passos: 1. Cliente compra com PIX e o pagamento é aprovado (pedido `received`). 2. Super admin chama `POST /v1/admin/orders/{id}/refunds` com o valor total pago. 3. Consultar o pedido; a loja chama `POST /v1/stores/{id}/orders/{id}/accept`. 4. Tentar `POST /v1/admin/orders/{id}/cancel`.
Esperado: RN-08 ("Qualquer estado | admin | cancelar e estornar total/parcial, motivo obrigatório, auditado") e WB-109: o admin cancela o pedido e o estorno acompanha; pedido totalmente estornado não segue o fluxo (loja não aceita, logística não despacha).
Obtido: (a) a rota de cancelamento do admin não existe (404); o único instrumento do admin é o estorno; (b) após o estorno total (200, `done`, restante 0) o pedido continua `received`; (c) a loja aceita (200) e pode marcar pronto; a logística cria corrida e despacha um motoboy para um pedido cujo dinheiro já voltou ao cliente.
Impacto: perda de dinheiro e pedido/pagamento inconsistente em operação normal (não exige ataque): o cliente é reembolsado e ainda recebe o produto, ou a loja separa um pedido devolvido. O Security classificou como Baixa (SEC-151) olhando só o ator malicioso; no uso comum do financeiro é Alta. Contorno: avisar a loja por fora; não há contorno no sistema.
Sugestão (dono: backend-dev/PO): rota `POST /v1/admin/orders/{id}/cancel` (motivo, estorno total opcional) e regra "estorno que zera o pedido o leva a CANCELADO (ator admin) e cancela a corrida".
Evidência: probe de 2026-11-19 (`status após estorno total: received`; `accept: 200`; `/cancel: 404`) e os dois testes `it.fails` acima. História relacionada: WB-109, WB-154, SEC-039/SEC-151.

**Reteste de 2026-11-19 (QA, Onda 7):** Reteste contra a API real (HEAD `b550088`, PostgreSQL 18.6 + PostGIS 3.6 e Redis 8 reais (compose do repositório), provedor `fake`; saída em `docs/qa/retestes/resultados/onda-7-saida.txt`, seção bug011): 11 de 11. (a) `POST /v1/admin/orders/{id}/cancel` em pedido pago: 200, `cancelled`, estorno = total, restante 0; (b) o cliente vê cancelado e pagamento `refunded`; (c) a loja que tenta aceitar depois recebe 409; (d) repetir é idempotente; (e) o estoque volta (50/2 -> 46/2 com o pedido -> 50/2); (f) o defeito original: **estorno total manual leva o pedido a `cancelled`** e o aceite da loja passa a 409; (g) estorno parcial mantém o pedido ativo; (h) pedido entregue: 409 `ORDER_NOT_CANCELLABLE`; (i) motivo curto: 400; (j) cliente comum na rota de admin: 403; (k) pedido pronto para coleta: a corrida é cancelada junto. A rota exige reautenticação recente do admin (403 `REAUTH_REQUIRED` observado e correto).
