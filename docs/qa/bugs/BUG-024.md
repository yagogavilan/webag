# BUG-024 | Severidade: Média | Prioridade: P2 | Status: ABERTO (achado do reteste da Onda 7; bloqueia o CI verde)

**Os testes e2e `reports` e `marketing-push` quebram no `beforeAll` desde o SEC-169 (cidade do CEP): 14 testes de WB-122 e WB-197 deixam de rodar**

Ambiente: API HEAD `b550088` (o commit que mudou o comportamento é `ceebc28`, "CEP must exist, geocoder configurable and off by default ... (SEC-169)"), suíte e2e com banco e Redis reais. Determinístico: falha também rodando os 2 arquivos sozinhos.
Passos: `pnpm --filter @webag/api exec vitest run --config ./vitest.config.e2e.ts test/reports.e2e-spec.ts test/marketing-push.e2e-spec.ts`.
Esperado: os dois arquivos passam (WB-122 relatórios operacionais; WB-197 push segmentado).
Obtido: `expected 201 "Created", got 422` em `marketing-push.e2e-spec.ts:27` (`customerInCity`) e `reports.e2e-spec.ts:42` (`mk`): os testes criam endereço com CEP `07900-100` (Francisco Morato) mas com uma cidade inventada pelo próprio teste (`Cidade Push xxxxxx`, `Cidade Rel xxxxxx`); desde o SEC-169 o servidor recusa CEP e cidade que não batem (`ADDRESS_CEP_CITY_MISMATCH`), então todos os testes do arquivo são pulados (8 + 6). Resultado da execução completa: 688 passaram, 15 pulados, só o `it` de reprodução do BUG-020 falhou, mas a cobertura de relatórios e de push segmentado está desligada.
Impacto: o CI da API fica vermelho (ou, se alguém "resolver" pulando, perde cobertura de duas funcionalidades). O backend avisou que o e2e completo não havia sido reexecutado depois da última correção: confirmado.
Sugestão (dono: backend-dev): nos dois helpers usar um CEP da cidade do cenário (o provedor `fake` mapeia o prefixo do CEP para a cidade: `079` Francisco Morato, `078` Franco da Rocha, `077` Caieiras) ou o `GEOCODING_PROVIDER` de teste que aceite qualquer CEP. História relacionada: WB-122, WB-197, SEC-169.
