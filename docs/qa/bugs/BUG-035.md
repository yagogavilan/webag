# BUG-035 | Severidade: Baixa | Prioridade: P3 | Status: ABERTO

**Pool do banco esgotado (timeout de conexão de 3 s) vira HTTP 500 com "Erro não tratado" e pilha completa no log, em vez de 503 com `Retry-After`**

Ambiente: commit `d1be18e`, API compilada com os caches da descoberta DESLIGADOS (TTL 0), PostgreSQL 16 local, `DB_POOL_MAX=10`, 1.000 usuários virtuais no perfil realista (`docs/qa/carga/carga-api.mjs`). Configuração de teste, não a de produção.
Passos: 1. Subir a API com `FEED_DIRECTORY_TTL_SECONDS=0 HOME_SECTIONS_TTL_SECONDS=0 BROWSE_CACHE_TTL_SECONDS=0`. 2. Rodar `VUS=1000 THINK_MIN_MS=5000 THINK_MAX_MS=15000 DURATION_S=60 RAMP_S=20 node docs/qa/carga/carga-api.mjs`.
Esperado: sob saturação, resposta curta e explícita de indisponibilidade (503 + `Retry-After`, sem pilha) para o cliente tentar de novo; um log de uma linha por janela.
Obtido: 405 respostas HTTP 500 (mais 153 estouros de 30 s no cliente; 11,26% de erro) e 407 entradas `ERROR ... Erro não tratado` com a pilha do `DrizzleQueryError` ("caused by: Error: timeout exceeded when trying to connect"). Com os caches ligados (configuração de produção) a mesma carga deu 0 erro e nenhum desses logs, então o risco é de saturação futura (pico, réplica a menos, banco lento), não do desenho atual.
Impacto: o app recebe 500 (tratado como erro do servidor, com retentativa); o volume de log com pilha por requisição piora a saturação. Sem efeito em dinheiro nem em dado.
Sugestão: mapear a falha de conexão do pool (e `statement_timeout`, código 57014) para 503 `SERVICE_UNAVAILABLE` com `Retry-After: 2` e log em `warn` agregado.
Evidência: `docs/qa/performance/resultados/qa-cacheoff-1000R.txt` e `.json` (status 500: 405, ERR: 153); log da API (`Failed query ... timeout exceeded when trying to connect`).
História relacionada: DT-082/ADR-017 (capacidade); item 1 de `docs/qa/performance/api-2026-11-22.md` §8.
