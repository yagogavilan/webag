# BUG-025 | Severidade: Média | Prioridade: P2 | Status: FECHADO em 2026-11-19 (reteste G4 final; resíduo Baixa na documentação)

**O armazenamento local (RustFS do `docker-compose.yml`) não tem CORS nos buckets: o upload de foto e documento pelo navegador não funciona no ambiente padrão do repositório**

Ambiente: `pnpm run setup` do zero (RustFS 1.0.6), painel web em `http://localhost:3101` (o mesmo vale para `3001`), Chrome. Playwright real: `PW_CHANNEL=chrome REAL_API_URL=http://localhost:3300 pnpm exec playwright test -c playwright.real.config.ts` em `apps/web`.
Passos: 1. Painel do lojista, etapa 3 do cadastro, escolher o documento e aceitar o recorte. 2. A API devolve a URL assinada do bucket (`http://localhost:9000/...`) e o navegador faz a preflight `OPTIONS`.
Esperado: o upload conclui ("Enviado").
Obtido: a etiqueta do documento fica em "Sem conexão. Retomamos o envio quando você voltar." (Playwright real, teste 1, 38 tentativas em 20 s). `curl -i -X OPTIONS http://localhost:9000/webag-private/x -H "Origin: http://localhost:3101" -H "Access-Control-Request-Method: PUT"` devolve 200 **sem** `Access-Control-Allow-Origin` (também para `http://localhost:3001`). `infra/storage-init.sh` só cria os buckets e a política de leitura pública; não aplica CORS. O trace do Playwright mostra `POST http://localhost:9000/webag-private` com status -1 (bloqueado, sem resposta): o upload é um **POST de formulário assinado (presigned POST)** para o bucket. Primeiro apliquei `put-bucket-cors` (origem `http://localhost:3101`, métodos GET, PUT, HEAD) e a preflight passou a devolver `access-control-allow-origin`, mas o upload continuou falhando (o método POST não estava na lista). Com `AllowedMethods` = GET, PUT, POST, HEAD e as origens `http://localhost:3101` e `http://localhost:3001` nos dois buckets, o Playwright real passou: cadastro de loja com 3 documentos, aprovação pelo admin, moderação (5 de 5) e a jornada pedido-entrega-troca (3 de 3). Causa confirmada.
Impacto: quem seguir o README e abrir o painel no navegador não consegue cadastrar loja com documento nem foto de produto; o app nativo não sofre (CORS é do navegador), mas o app no navegador (DEC-058) sim. Em produção (R2) o guia de deploy já manda configurar o CORS do bucket (`guia-deploy.md` linha 526).
Sugestão (dono: tech-lead/backend-dev): `storage-init.sh` aplicar `put-bucket-cors` com as origens do `CORS_ORIGINS` do `.env` (3001, 3101, 8081) e métodos GET, PUT, **POST** e HEAD; acrescentar o passo ao `setup-do-zero.md`. História relacionada: WB-052, WB-060, DT-067, DEC-058.

**Reteste G4 final (2026-11-19, QA, commit congelado 0d902ab; saídas em `docs/qa/retestes/resultados/g4-*.txt`):** do zero, sem nenhum ajuste manual no contêiner: o `pnpm run setup` aplicou o CORS (GET, PUT, POST, HEAD) nos dois buckets para `3001`, `3101` e `8081` (preflight OPTIONS devolve `Access-Control-Allow-Origin` e `POST`, 6 de 6) e o upload real de foto pelo POST assinado com `Origin` do navegador deu 204 no bucket e `complete` 200. O Playwright real passou **8 de 8** (`playwright.real.config.ts`, 3 ignorados são as capturas `CAPTURE_V3`). **Resíduo (Baixa, tech-lead):** o padrão de `REAL_DB_URL` em `e2e-real/04-pedido-entrega-troca.e2e.ts` ainda é `localhost:5432/webag_qa35e` (um banco antigo do QA); o teste 04 só passa com `REAL_DB_URL` apontando para o banco do `pnpm run setup` (o README cita a variável, mas o padrão continua errado). Nesta rodada: `REAL_DB_URL=postgresql://webag:webag_dev_only@localhost:5433/webag`.
